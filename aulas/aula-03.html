01Visão Geral e Objetivos de Aprendizagem

A Aula 02 deixou o repositório de cada grupo com um projeto Maven versionado e sincronizado no GitHub. Hoje entram em cena dois problemas práticos: como duas ou mais pessoas trabalham na mesma base de código sem sobrescrever o trabalho uma da outra, e como transformar a conversa com a entidade parceira em requisitos que orientam o que programar. Fechamos avançando a camada de acesso a dados do TenisShop.

02Articulação com a Entidade Parceira: Levantamento de Requisitos

Antes de programar qualquer tela ou regra de negócio, o grupo precisa entender o problema do ponto de vista de quem vai usar o sistema. É isso que o cronograma da disciplina chama de "início do desenvolvimento do software": ainda não é escrever código, é escrever com clareza o que o código vai precisar resolver.

Por que Conversar com a Entidade Antes de Codar?

Um sistema construído sem ouvir quem vai usá-lo tende a resolver o problema errado, por mais bem escrito que o código esteja. A entidade parceira conhece a rotina, as exceções do dia a dia e as regras não escritas do processo atual; é ela quem aponta o que realmente precisa mudar.

Roteiro para a Primeira Reunião

Leve estas perguntas para a conversa com a entidade parceira (presencial, remota ou por formulário) e registre as respostas por escrito:

Processo Atual

Como essa tarefa é feita hoje? Em papel, planilha, outro sistema? Quantas pessoas participam?

Problemas

O que mais atrasa, gera erro ou se repete sem necessidade no processo atual?

Usuários

Quem vai usar o sistema no dia a dia? Existem perfis diferentes de acesso, como administrador e operador?

Dados

Quais informações precisam ser cadastradas, consultadas ou geradas em relatório?

Prioridades

Se o software só pudesse resolver uma coisa neste semestre, qual seria?

Da Conversa para a Lista de Funcionalidades

Depois da reunião, traduza as respostas em frases curtas no formato "o sistema deve permitir que [usuário] [ação]". Essa lista inicial orienta as próximas aulas técnicas e compõe parte da Avaliação B (entrega do software e documentações), prevista no plano de ensino.

markdown
## Requisitos Levantados com [Nome da Entidade] em [Data]

1. O sistema deve permitir que o(a) administrador(a) cadastre novos usuários com perfil de acesso.
2. O sistema deve permitir que o(a) operador(a) registre [ação principal do domínio].
3. O sistema deve gerar um relatório de [dado relevante] por período.
4. ...
Onde registrar: inclua essa lista no README.md do repositório do grupo, na seção de contexto, ou em um arquivo próprio (docs/requisitos.md). O professor acompanha o avanço pela planilha de cada grupo, apresentada na Aula 01.

03Branches no Git: Trabalho Paralelo sem Pisar no Colega

Na Aula 02 o grupo trabalhou direto na branch main, alternando quem fazia push e avisando os colegas antes. Isso funciona com poucas mudanças pequenas, mas fica arriscado assim que duas pessoas mexem no mesmo arquivo ao mesmo tempo. As branches de funcionalidade resolvem esse problema.

Por que não Trabalhar Direto na Main?

A branch main deve sempre representar uma versão que funciona, pronta para ser mostrada à entidade parceira. Se cada integrante desenvolve direto nela, um código incompleto ou com erro fica visível para o grupo inteiro até ser corrigido. Uma branch de funcionalidade isola o trabalho em andamento: só volta para a main quando estiver pronto.

Criando e Alternando entre Branches

bash
# Lista as branches locais (a atual aparece com *)
git branch

# Cria uma nova branch de funcionalidade e já muda para ela
git checkout -b feature/usuario-dao

# Alterna de volta para uma branch já existente
git checkout main

Padrão de Nomenclatura de Branches

PrefixoQuando usarExemplo
feature/Nova funcionalidadefeature/usuario-dao
fix/Correção de um bugfix/validacao-email
docs/Documentaçãodocs/requisitos-entidade

Mesclando uma Branch (Merge)

Quando a funcionalidade estiver pronta e testada, volte para a main e traga as mudanças da branch com git merge:

bash
# Garanta que está na main antes de mesclar
git checkout main

# Traz as mudanças da branch de funcionalidade para a main
git merge feature/usuario-dao
main
──▶git checkout -b
feature/...
──▶commits
feature/... pronta
──▶git merge
main atualizada

Conflitos de Merge: o que são e como resolver

Um conflito acontece quando a mesma linha de um arquivo foi alterada de formas diferentes na main e na branch de funcionalidade, e o Git não consegue decidir sozinho qual versão manter. O arquivo fica marcado assim:

plaintext
<<<<<<< HEAD
    private Boolean ativo;
    private Double desconto;
=======
    private Boolean ativo;
    private Integer estoqueMinimo;
>>>>>>> feature/categoria-estoque

Nada está quebrado: o Git só está pedindo uma decisão humana. O trecho entre <<<<<<< HEAD e ======= é o que já estava na main; o trecho entre ======= e >>>>>>> é o que veio da branch.

Passo a passo para resolver um conflito
  1. Abra o arquivo indicado pelo Git (ele aparece na saída do git merge como "CONFLICT").
  2. Converse com quem editou a outra parte e decida juntos o conteúdo final.
  3. Edite o arquivo mantendo só o resultado desejado e apague as três linhas de marcação (<<<<<<<, =======, >>>>>>>).
  4. Adicione o arquivo resolvido e conclua o merge com um commit.
bash
# Depois de editar o arquivo e remover os marcadores
git add Categoria.java

# Conclui o merge com um commit
git commit -m "merge: resolve conflito entre desconto e estoqueMinimo em Categoria"

04Prática Guiada: Criando, Mesclando e Resolvendo Conflitos

Aplique agora o fluxo de branches no repositório do seu grupo. Os passos abaixo usam a classe Categoria.java, criada na Aula 02, como exemplo; adapte o nome da branch e do atributo para a funcionalidade real que seu grupo está implementando.

Passo 1: Atualize a Main Antes de Começar

bash
git checkout main
git pull origin main

Passo 2: Crie a Branch de Funcionalidade

bash
git checkout -b feature/categoria-estoque

Passo 3: Trabalhe e Faça Commits Normalmente

Edite os arquivos necessários dentro da branch e registre o progresso com commits pequenos e frequentes, como já praticado na Aula 02:

bash
git add .
git commit -m "feat: adiciona atributo de estoque minimo na Categoria"

Passo 4: Volte para a Main e Mescle

bash
git checkout main
git merge feature/categoria-estoque
Se aparecer "CONFLICT": siga o passo a passo da Seção 03 antes de continuar. Só avance para o próximo passo depois que o git status não mostrar mais nenhum arquivo em conflito.

Passo 5: Envie a Main Atualizada ao GitHub

bash
git push origin main

05Avanço no Projeto Exemplo TenisShop: Camada DAO

Com a ConexaoBanco pronta desde a Aula 02, o TenisShop ganha hoje sua primeira classe de negócio real: uma DAO que efetivamente lê dados da tabela usuarios. É esse tipo de entrega, uma funcionalidade isolada e testável, que deve nascer dentro de uma branch, seguindo o fluxo da Seção 04.

Até onde ir hoje: o TenisShop segue como exemplo de referência construído ao longo do semestre, conforme o cronograma da Aula 01. O que se espera de cada grupo hoje é aplicar a mesma técnica: uma branch de funcionalidade com pelo menos um método de DAO, mesmo que simples, para a entidade central do projeto do grupo. Não é preciso reproduzir a UsuarioDAO inteira, só a mesma ideia.

Relembrando o Padrão DAO

Como visto na Aula 02, uma DAO isola tudo o que envolve SQL: montar a consulta, executar, e transformar cada linha da tabela em um objeto de domínio. Nenhuma outra parte do sistema deve escrever SQL diretamente; ela só chama métodos da DAO.

Por que PreparedStatement em vez de Statement?

A UsuarioDAO usa PreparedStatement para montar as consultas SQL. Diferente de concatenar texto direto na string do comando, o PreparedStatement separa o comando dos valores: o ? é substituído com segurança por setString, setInt e métodos equivalentes. Isso evita um ataque conhecido como SQL Injection, em que alguém digita um valor malicioso (por exemplo, ' OR '1'='1) esperando alterar o comando SQL que será executado.

Classe UsuarioDAO.java

Local: src/main/java/br/edu/ifsul/venancio/tenisshop/model/dao/UsuarioDAO.java

java
package br.edu.ifsul.venancio.tenisshop.model.dao;

import br.edu.ifsul.venancio.tenisshop.model.domain.Usuario;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

/**
 * Classe responsável pelo acesso a dados da entidade Usuario.
 * Aplica o padrão de projeto DAO (Data Access Object).
 *
 * @author Geovane Griesang
 */
public class UsuarioDAO {

    /**
     * Lista todos os usuários cadastrados no banco de dados.
     * @return List<Usuario> lista de usuários encontrados
     * @throws SQLException caso ocorra falha na consulta
     */
    public List<Usuario> listarTodos() throws SQLException {
        List<Usuario> usuarios = new ArrayList<>();
        String sql = "SELECT id, nome, email, senha, perfil, ativo FROM usuarios ORDER BY nome";

        Connection conexao = ConexaoBanco.getConexao();
        try (PreparedStatement stmt = conexao.prepareStatement(sql);
             ResultSet rs = stmt.executeQuery()) {

            while (rs.next()) {
                usuarios.add(mapearUsuario(rs));
            }
        }
        return usuarios;
    }

    /**
     * Busca um usuário pelo e-mail cadastrado.
     * @param email e-mail do usuário buscado
     * @return Usuario encontrado, ou null se não existir
     * @throws SQLException caso ocorra falha na consulta
     */
    public Usuario buscarPorEmail(String email) throws SQLException {
        String sql = "SELECT id, nome, email, senha, perfil, ativo FROM usuarios WHERE email = ?";

        Connection conexao = ConexaoBanco.getConexao();
        try (PreparedStatement stmt = conexao.prepareStatement(sql)) {
            stmt.setString(1, email);

            try (ResultSet rs = stmt.executeQuery()) {
                if (rs.next()) {
                    return mapearUsuario(rs);
                }
            }
        }
        return null;
    }

    private Usuario mapearUsuario(ResultSet rs) throws SQLException {
        Usuario usuario = new Usuario();
        usuario.setId(rs.getInt("id"));
        usuario.setNome(rs.getString("nome"));
        usuario.setEmail(rs.getString("email"));
        usuario.setSenha(rs.getString("senha"));
        usuario.setPerfil(rs.getString("perfil"));
        usuario.setAtivo(rs.getBoolean("ativo"));
        return usuario;
    }
}
