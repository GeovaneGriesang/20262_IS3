01Visão Geral e Objetivos desta Semana

Nesta semana, a disciplina não tem encontro presencial: o professor acompanha a delegação de estudantes do IFSul nas finais dos Jogos dos Institutos Federais (JIFs), em Pelotas/RS. Em vez de pausar o semestre, esta aula transforma a semana em tempo protegido de agenda para cada grupo avançar no próprio projeto, no seu próprio ritmo.

Trabalho remoto e assíncrono não é uma situação de exceção rara no mercado: é como boa parte das equipes de desenvolvimento de software funciona no dia a dia, coordenando por commits, mensagens e documentação em vez de estar sempre na mesma sala. A Aula 05 é, também, uma primeira prática guiada disso — com commits pequenos e bem descritos, cada pessoa do grupo consegue entender o que mudou mesmo sem ter visto acontecer ao vivo.

Objetivos de Aprendizagem

  • Avançar o projeto do grupo de forma autônoma, sem supervisão direta em tempo real.
  • Praticar o fluxo de Git/GitHub como principal ferramenta de coordenação remota da equipe.
  • Aplicar, no projeto de cada grupo, técnicas já ensinadas (Enum, hash de senha, MVC, DAO e, opcionalmente, os recursos de autenticação da Aula 04).
  • Registrar dúvidas e bloqueios de forma assíncrona, sem travar o progresso enquanto espera resposta.
O que muda em relação às aulas anteriores: não há um "Passo a Passo" único que a turma toda segue junto. A Seção 02 apresenta várias frentes de trabalho possíveis — cada grupo escolhe a que faz mais sentido para o estágio atual do seu projeto.

02Frentes de Trabalho: Escolha Conforme o Estágio do Grupo

Os grupos estão em pontos diferentes do projeto. Reveja o repositório do grupo, decida com a equipe (mesmo que por mensagem, à distância) qual frente abaixo é a prioridade da semana, e dividam entre si quem toca cada parte.

Avançar o CRUD da entidade central

Se a camada de domínio e DAO do sistema do grupo ainda está incompleta, este é o momento de seguir o padrão de UsuarioDAO (Aulas 02 e 04) e implementar inserir, listarTodos, atualizar e excluir para a entidade principal da parceria com a entidade.

Aplicar autenticação e senha forte

Se o sistema do grupo já tem (ou vai ter) conceito de usuário e login, vale trazer as ideias da Aula 04 para o projeto próprio: perfis por Enum, hash BCrypt, e — se fizer sentido para a entidade parceira — troca de senha, medidor de força e/ou recuperação por e-mail.

Construir as telas JavaFX

Para grupos com o Model e o DAO já prontos, é hora de avançar a View: telas de listagem, cadastro e edição em FXML, com o Controller ligando tudo — reaproveitando o padrão MVC visto na tela de login (Aula 04, Seção 07).

Documentação e alinhamento com a entidade

Atualizar o README.md do repositório, revisar a lista de requisitos (Aula 03, Seção 02) e, se surgiram dúvidas sobre o que a entidade parceira precisa, registrar as perguntas para a próxima conversa — presencial ou remota — com ela.

Scripts SQL versionados

Se o schema do banco do grupo já mudou várias vezes só por comandos manuais no MySQL Workbench, aproveite para organizar isso como scripts numerados (V1, V2...), seguindo o padrão da Aula 04, Seção 12.

Rotina Sugerida (adapte à realidade do grupo)

  1. Antes de começar: git pull origin main, para garantir que está trabalhando sobre a versão mais recente do projeto.
  2. Combine com o grupo (mensagem, chamada de vídeo, o que for viável) quem mexe em qual parte, para não duplicar trabalho nem gerar conflitos de merge grandes.
  3. Trabalhe em uma branch feature/... para cada funcionalidade, como já vem sendo feito desde a Aula 03.
  4. Faça commits pequenos e frequentes, com mensagens no padrão Conventional Commits (Aula 02, Seção 03) — são eles que vão contar a história da semana para o resto do grupo e para o professor.
  5. Ao final de cada sessão de trabalho, mesmo que a funcionalidade não esteja 100% pronta: push para o GitHub. Código que só existe na sua máquina não existe para o grupo.

03Suporte à Distância e Regras do Trabalho Remoto

Sem aula presencial, o suporte do professor acontece de forma assíncrona. Isso muda um pouco como pedir (e esperar) ajuda.

Como Pedir Ajuda

  1. Publique a dúvida no Moodle da disciplina, no fórum ou espaço indicado para a Aula 05.
  2. Descreva o problema de um jeito que alguém sem estar vendo sua tela consiga entender: o que você tentou fazer, o comando ou trecho de código, e a mensagem de erro completa (print ou texto colado, não só "não funciona").
  3. Enquanto espera resposta, siga para outra frente da Seção 02 em vez de travar esperando — como em qualquer equipe remota, é normal ter mais de uma tarefa em andamento.
O professor volta a acompanhar o Moodle com regularidade a partir do fim da semana dos JIFs; dúvidas urgentes de bloqueio total (ex.: "não consigo nem abrir o projeto") têm prioridade de resposta.

Regras de Ouro do Trabalho Remoto (adaptadas das regras de laboratório)

  1. Se for usar um computador que não é o seu (biblioteca, casa de um colega, laboratório de outra disciplina): confira a identidade do Git antes de commitar (git config user.name / user.email), como na Aula 02, Seção 02.
  2. Nunca deixe credenciais (senha do MySQL, Personal Access Token do GitHub, email.properties da Aula 04) salvas num computador que não é seu, nem as envie por mensagem de texto ou e-mail sem necessidade.
  3. Antes de encerrar cada sessão de trabalho, confirme que o push foi concluído — não há garantia de que o próximo acesso será na mesma máquina.
  4. Se o grupo trabalhar em paralelo, avise no grupo/chat quando começar e quando terminar uma tarefa, para reduzir a chance de dois integrantes mexerem na mesma parte do código ao mesmo tempo.

04Checklist e Critérios para Avaliação Processual

A avaliação processual contínua não pausa nesta semana — ela só passa a ser verificada pelo histórico do repositório, em vez de observação direta em sala. Verifique estes itens antes do fim da semana:

  • Pelo menos um commit por integrante do grupo, com mensagem descritiva no padrão Conventional Commits.
  • Todo o trabalho da semana enviado (push) para a branch main do repositório do grupo — nada ficou parado só numa máquina local.
  • Nenhuma branch de funcionalidade (feature/...) esquecida sem merge, se o trabalho nela já estiver pronto.
  • Se houve algum bloqueio, ele foi registrado no Moodle (mesmo que a resposta ainda não tenha chegado) — bloqueio não registrado não pode ser considerado na avaliação.
  • O grupo consegue explicar, na próxima aula presencial, o que cada commit da semana fez e por quê.
  • Nenhuma credencial (senha de banco, Personal Access Token, email.properties) foi commitada por engano — confira com git status e git log antes de considerar a semana concluída.
